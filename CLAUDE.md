# CLAUDE.md

Este arquivo fornece orientações ao Claude Code (claude.ai/code) ao trabalhar com código neste repositório.

## Visão geral do projeto

erp_Novagest é um ERP modular. Cada módulo de negócio é uma "tela" do sistema, mas **todos os módulos compartilham um único banco de dados Azure SQL e uma única API backend**. Não existe banco de dados por módulo — novos módulos adicionam tabelas/rotas à estrutura já existente. Hoje existem três módulos de negócio: o **Ranking** (placar diário de vendas por rede — agrupadas por diretor —, com gerador de relatório pronto para WhatsApp), o **Margens** (lançamento diário de margem de lucro por loja física, com resumo/relatório de período e exportação em PDF) e o **Marketing** (lançamento mensal de faturamento geral × faturamento vindo de marketing × faturamento vindo de cliente retorno/indicação, por loja física, com percentual e comparação subiu/caiu/igual contra o mês anterior calculados automaticamente — substitui uma planilha manual). Os três consomem uma camada compartilhada de **Cadastros** (Diretor/Rede/Loja/Responsavel, sob `/api/cadastros/*`), que não tem tela própria — é CRUD comum reaproveitado pelos módulos de negócio (e por qualquer módulo futuro que precise da mesma hierarquia). Além disso, o sistema tem uma camada transversal de **autenticação + administração de usuários** (login, JWT, tela de gestão de usuários) que protege todos os módulos. Existe ainda um quarto sub-sistema, **Controle de Ligações** — diferente dos três acima, ele é deliberadamente isolado do resto do ERP (login próprio, casca de layout própria, invisível pro usuário comum) — descrito em detalhe mais abaixo, perto da seção de autenticação, já que depende diretamente do novo campo `role` de `Usuarios`.

O repositório tem dois aplicativos independentes, sem ferramentas compartilhadas:
- `backend/` — API REST em Node.js/Express
- `frontend/` — SPA em React 19 + Vite

**Frontend e backend estão integrados.** `RankingPage.jsx` busca `diretores` (cada um com suas `redes[]` aninhadas), `categorias` e `entradas` via HTTP (helper em `frontend/src/modulos/ranking/rankingApi.js`) e persiste valores no `onBlur` de cada input — não há mais estado fictício inicial. O mesmo handler de blur (`onBlurSave`, em `RankingPage.jsx`) decide entre duas rotas conforme o valor digitado: `POST /api/ranking/entradas` (upsert) quando o valor é diferente de zero; `DELETE /api/ranking/entradas?data=...&categoriaId=...&redeId=...` (via `removerEntrada` em `rankingApi.js`) quando o valor é zero — para apagar de fato uma entrada salva anteriormente em vez de só deixar de persistir, evitando que o campo "volte" sozinho pro valor antigo depois de zerado de propósito. O contrato exato de cada rota (formato de request/response, status codes) está documentado em `CONTRATO-RANKING-API.md` na raiz do repo; consulte-o antes de mudar o formato de qualquer endpoint do Ranking. A URL base da API vem da variável de ambiente Vite `VITE_API_URL` (ver `frontend/.env.example`) — nunca hardcode a URL no componente.

**Hierarquia de dados do Ranking (v2 — Diretor > Rede).** O Ranking passou por uma mudança de arquitetura: a hierarquia era de 2 níveis (`Redes` > `Lojas`) e virou 3 níveis (`Diretores` > `Redes` > Loja física). O que antes era a tabela `Redes` (ex: "Rede V. Hugo") agora é `Diretores`; o que antes era `Lojas` (Delta, Lendários, Ouro...) agora é `Redes`. O Ranking **continua operando só no nível Diretor → Rede** — ele nunca lançou/lança valor por loja física; a tabela `Lojas` física existe no banco (módulo Margens) mas não é consumida por nenhuma rota do Ranking. Ver seção "Schema do Ranking" abaixo para os campos exatos de cada tabela após a migração.

Ao carregar a página (ou trocar a data), o frontend busca as entradas de **todas** as categorias em paralelo (`Promise.all`) e guarda tudo no estado `entries` — não busca sob demanda ao trocar de aba. Isso é proposital: garante que "Gerar relatório do dia" sempre reflita o que está salvo no banco, independente de quais categorias o usuário visitou na sessão. Ao mexer nesse fluxo, preserve esse comportamento (não volte a buscar só a categoria ativa).

A `ConfigView` de `RankingPage.jsx` (rotulada na tela como "Diretores e redes") faz CRUD real de **diretores e redes** contra o backend (`POST/PUT/DELETE /api/cadastros/diretores` e `/redes`, via `cadastrosApi.js` — ver módulo Cadastros abaixo): criar/editar só atualiza o estado local depois que a API confirma, usando o id real retornado; remover só some do estado local após a API confirmar. **Categorias deixaram de ser 100% em memória** — agora têm CRUD real contra `/api/ranking/categorias` (`fetchCategorias`/`criarCategoria`/`atualizarCategoria`/`removerCategoria` em `rankingApi.js`), documentado em `CONTRATO-RANKING-API.md` (seções 1–4). Existem 3 categorias **padrão** (Receita Bruta, Correção, Acessórios, `padrao=1`) que nunca podem ser excluídas via API (`409`), só ocultadas (`PUT` com `visivel:false`); categorias novas nascem com `padrao=false` e podem ser excluídas de verdade se não tiverem nenhum lançamento vinculado (`409` caso contrário). Igual ao caso de `PUT /api/cadastros/redes/:id` documentado abaixo, as rotas de escrita de categorias (`POST`/`PUT`/`DELETE /api/ranking/categorias`) não têm `adminMiddleware` nenhum — rodam só com o `authMiddleware` do mount; o botão de criar/editar/ocultar/excluir categoria em `ConfigView.jsx` só é renderizado quando `isAdmin === true`, mas isso é trava de UI, não de backend.

`Redes` (o nível Delta/Lendários, filho de um Diretor) tem campos `visivel` e `ativo` (ambos BIT, default `1`) persistidos no banco — `Diretores` não tem nenhum dos dois. Uma rede com `visivel=false` some do grid principal (filtrada do array antes do `.map`, não `display:none`, para o grid CSS reajustar sozinho) e é excluída de `buildFullReport`; `ativo=false` é o soft-delete real (ver seção de exclusão abaixo). Os dois são controles **separados** na `ConfigView` ("Ocultar/Mostrar" para `visivel`, "Desativar/Reativar" para `ativo`) — decisão intencional, não é duplicação acidental. O toggle "Ocultar/Mostrar" só é renderizado quando `isAdmin === true` (via `AuthContext`), e mora em cada **linha de Rede** dentro do card do relatório (não mais no cabeçalho do card, que agora representa um Diretor sem campo `visivel` próprio) — mas essa restrição existe **só no frontend**: `PUT /api/cadastros/redes/:id` não tem `adminMiddleware` nem qualquer checagem de admin no backend (roda só com `authMiddleware`, igual ao resto de `/api/cadastros`), então qualquer usuário autenticado que chame a rota diretamente (curl/Postman) pode alterar `visivel`/`nome`/`emoji`/`ativo`/`responsavelId` de qualquer rede. Ao mexer nessa rota, não presuma que existe uma trava de admin no backend só porque a UI esconde o botão.

**Cadastros é uma camada compartilhada, sem tela própria.** `Diretor > Rede > Loja` (mais `Responsavel`, rotulado "GG" na UI) não pertence a nenhum módulo de negócio — o CRUD inteiro vive em `/api/cadastros/*` e é consumido tanto pela `ConfigView` de `RankingPage.jsx` (CRUD de Diretor/Rede) quanto por `MargensPage.jsx` (só leitura, `fetchRedes()`, pra montar o `<select>` de Rede/Loja do lançamento). No frontend, o helper fica em `frontend/src/lib/cadastrosApi.js`, ao lado de `apiClient.js` — não dentro de `modulos/ranking/` ou `modulos/margens/` — justamente por ser compartilhado. Esse módulo nasceu de uma extração: o CRUD de Diretor/Rede/Responsavel vivia antes em `/api/ranking/*` (ver nota de migração no topo de `CONTRATO-RANKING-API.md`). Ver seção "Arquitetura" abaixo pro CRUD completo, as regras de exclusão e o módulo Responsaveis.

**Margens é o segundo módulo de negócio** (`MargensPage.jsx`, duas views internas: "Lançamento", padrão, e "Relatório de período"). O modelo de dados tem uma pegadinha: `faturamento` e `custoProduto` (custo geral de produtos) são valores **consolidados da franquia inteira** — o mesmo número vale pra todas as lojas naquele dia, editáveis a qualquer momento na view de Lançamento, sem conceito de "confirmado". Por padrão, cada linha de loja mostra só o campo "Margem (%)" — o usuário cola ali a margem que um ERP externo já calculou, e a cor (`>=41%` verde, `>=40%` amarelo, senão vermelho) vem direto desse valor digitado, sem depender de nenhum outro campo. O `totalTar` (taxa de cartão daquela unidade) é secundário/opcional, escondido atrás do botão "Calcular pelo Total Tar"; quando revelado e preenchido, ele passa a mandar — a margem calculada a partir dele (`faturamento - custoProduto - totalTar`) sobrepõe a margem digitada, tanto na tela quanto no payload de confirmação. Ao confirmar uma loja (`POST /api/margens/entradas`), o backend grava o `totalTar` (digitado direto, ou derivado da margem via `totalTar = faturamento - custoProduto - margem/100*faturamento`) **junto com uma cópia (snapshot)** do faturamento/custoProduto consolidados usados naquele momento — histórico intencional, pra sobreviver a mudanças futuras nesses valores sem reescrever o cálculo de lançamentos já confirmados (ver schema de `MargensEntradas` abaixo); esse snapshot de faturamento/custoProduto vem sempre do bloco "Consolidado da franquia" atual, **independente de qual dos dois campos foi a fonte** — nunca é gravado zerado só porque a margem digitada foi o caminho usado (bug já corrigido). Quando a margem digitada é a fonte, ela também é enviada como `margemInformada` (ver schema abaixo) — um campo só de auditoria, que não entra em nenhum cálculo do relatório de período. Na tela, uma loja já confirmada no dia mostra o `totalTar` usado desabilitado, um "Margem informada: X%" ao lado quando a fonte foi a margem digitada, e um selo "✓ Confirmado" com botão "Editar" pra reabilitar (volta ao modo "margem" padrão); o botão "Confirmar" só fica habilitado depois que o usuário digita algo em pelo menos um dos dois campos (mesmo "0" conta como valor informado) — trava de UX proposital pra evitar confirmar margem calculada em cima de valor vazio por acidente. `GET /api/margens/relatorio?dataInicio=&dataFim=` soma o período por loja e calcula `lucro`/`percentualMargem`/`cor` agrupado Diretor→Rede→Lojas, sem nenhuma referência a `margemInformada`; os filtros de Rede/Cor/nome de loja na tela de relatório são aplicados 100% no frontend sobre esse resultado já buscado (mesmo princípio do Ranking, evita ida e volta ao servidor a cada filtro trocado). "Baixar PDF" usa `jsPDF`+`jspdf-autotable` inteiramente no navegador, sem rota nova no backend. Contrato completo em `CONTRATO-MARGENS-API.md` (v5) — consulte-o antes de mudar o formato de qualquer endpoint do Margens.

**Marketing é o terceiro módulo de negócio** (`MarketingPage.jsx`, granularidade **mensal por Loja física**, não por Rede — diferente do Ranking). A tela de Lançamento tem 3 abas: "Marketing" e "Cliente Retorno/Indicação" (cada uma edita uma parte do faturamento da loja no mês) e "Resumo Geral" (dashboard consolidado, sem filtro de diretor). As duas primeiras abas leem/escrevem no **mesmo objeto de estado por loja** (`valoresPorLoja`, com os 3 campos `faturamentoGeral`/`faturamentoMarketing`/`faturamentoRetornoIndicacao`) — não há estado duplicado por aba; a aba "Cliente Retorno/Indicação" mostra `faturamentoGeral` sempre somente-leitura (só é editável na aba "Marketing"); o vocabulário da frase de observação calculada troca conforme a aba — "RENDIMENTO" na aba Marketing (não "MARKETING", trocado depois pra bater com a planilha original), "RETORNO/INDICAÇÃO" na outra — mas a lógica de comparação por trás (`buildObservacao`, em `marketingFormat.js`) é a mesma função nas duas. O card de cada loja consolida o blur dos até 3 campos num único disparo por card (via `relatedTarget`, com fallback de debounce) antes de decidir o que fazer, em `handleBlurLoja` (`MarketingPage.jsx`): primeiro um dirty-check (não dispara nenhuma chamada de rede se nada mudou desde o último save/exclusão); se algo mudou, `POST /api/marketing/entradas` (upsert dos 3 valores) quando pelo menos um dos 3 é diferente de zero, ou `DELETE /api/marketing/entradas?ano=&mes=&lojaId=` (via `removerEntrada` em `marketingApi.js`) quando os 3 ficam zero/vazios — mesmo princípio do Ranking (campo zerado apaga a entrada em vez de persistir zerada), adaptado para um lançamento com 3 campos em vez de 1: zerar só 1 dos 3 não é motivo para excluir, é `POST` normal (zero pode ser dado real, ex.: nenhum retorno/indicação naquele mês). `GET /api/marketing/entradas?ano=&mes=` retorna só Redes e Lojas com `ativo = 1` (não filtra por `visivel`, que é um conceito só do grid do Ranking) como um array **flat** de blocos `{ diretor, rede, lojas[] }` — um item por Rede, **sem** nenhum campo `totais`/`redes[]` aninhado nem soma pronta por Diretor (confirmado em `marketing.service.js: agruparPorDiretorERede`); todo total exibido na tela (por Rede, por Diretor, dashboard) é calculado 100% no cliente, nunca vem pronto da API — a v1 de `CONTRATO-MARKETING-API.md` descreve esse GET com `totais`/`redes[]` aninhado, o que **não bate** com a implementação real; o contrato precisa de correção nesse ponto específico, não confie nele cegamente pra esse endpoint. A comparação (`subiu`/`caiu`/`igual`) por loja vem sempre calculada na leitura, nunca persistida — corrigir um lançamento antigo recalcula automaticamente a comparação do mês seguinte. Consulte `CONTRATO-MARKETING-API.md` (v1) antes de mudar o formato de qualquer endpoint do Marketing; a v1 deliberadamente deixa de fora o detalhamento por canal (TV, Instagram, OLX...) da planilha original, reservado para uma v2 futura.

**`RelatorioMarketing.jsx` — quarta view de `MarketingPage.jsx`, "Relatório de visão geral", separada das 3 abas de Lançamento** (acessada pelo botão "📊 Ver relatório de visão geral" no cabeçalho; mesmo mecanismo de troca de view — state `view` + botão `btnGhost` — que `MargensPage.jsx` já usa entre "Lançamento" e "Relatório de período"; o `diretorId` selecionado no cabeçalho é compartilhado entre as duas views, não se perde ao alternar). Período livre por dois `<input type="month">` (início/fim); busca um `GET /api/marketing/entradas?ano=&mes=` por mês do intervalo em paralelo, mais **um mês extra antes do início** (nunca vira coluna da tabela) só pra poder colorir a primeira coluna visível. Mostra só `percentualMarketing` por loja/mês (nenhum valor absoluto de faturamento) — a cor de cada célula compara o percentual com o mês **imediatamente anterior na mesma linha**, calculada 100% no cliente (`compararTotais`, de `marketingFormat.js`); é uma fonte de comparação **diferente** do campo `comparacao` que a API devolve por loja (que compara faturamento absoluto contra o mês anterior, não percentual) — não confundir as duas ao mexer nesse arquivo. Subtotal por Rede e Total geral do Diretor reaproveitam as mesmas `somarCampoLojas`/`percentualSobreTotal` de `marketingFormat.js` já usadas em `TotalGeralRow.jsx` (SOMA/SOMA, nunca média de percentuais individuais) — não existe um subtotal por Rede na tela de Lançamento em si, só aqui e no total por Diretor. "Baixar PDF" usa `jsPDF`+`jspdf-autotable` 100% no navegador (mesma abordagem do Margens, sem rota nova no backend), reproduzindo a mesma tabela e preservando a cor de cada célula via estilo por célula (fill/text RGB), não só texto em preto e branco.

`buildFullReport` (dentro de `RankingPage.jsx`) monta o texto de "Gerar relatório do dia" iterando **todos** os diretores e, dentro de cada um, **todas** as categorias (não só a aba ativa) e omite por completo qualquer categoria sem nenhum valor lançado; dentro de cada categoria incluída, também omite diretores sem nenhuma rede preenchida e, dentro de cada diretor, redes individuais sem valor (não aparecem como linha zerada) — e sempre respeita `visivel`/`ativo` das redes (não existe mais filtro no nível Diretor). Cada bloco de categoria tem cabeçalho em maiúsculas com o nome da categoria (`*RELATÓRIO <NOME> — DD/MM*`), inclusive a categoria principal, para deixar clara a separação entre categorias ao colar no WhatsApp.

**Autenticação é obrigatória para todo o sistema.** Login é por e-mail/senha (`POST /api/auth/login`) contra a tabela `Usuarios` já existente no banco (bcrypt para hash/verificação de senha), retornando um JWT (`JWT_SECRET`, expira em 12h) que o frontend guarda via `frontend/src/app/authStorage.js` e usa em todo request subsequente (header `Authorization: Bearer <token>`, injetado automaticamente por `frontend/src/lib/apiClient.js`). Além de `is_admin`, `Usuarios` ganhou uma coluna `role VARCHAR(30) NOT NULL DEFAULT 'usuario'` (`'admin' | 'usuario' | 'operador_cobranca'`) — os dois campos **coexistem**, `role` não substituiu `is_admin` (nenhuma rota recalcula um a partir do outro); `role` também vai pro payload do JWT e é populado em `req.usuario.role` por `authMiddleware`, ao lado de `id`/`email`/`isAdmin` que já existiam. Todas as rotas de `/api/ranking/*`, `/api/cadastros/*`, `/api/margens/*` e `/api/marketing/*` exigem sessão válida (`authMiddleware` aplicado no mount, em `app.js`, não rota a rota) — apenas `POST /api/auth/login`, `POST /api/auth/reativacao/login` (login separado do sub-sistema Controle de Ligações, ver abaixo), `POST /api/auth/esqueci-senha` e `POST /api/auth/redefinir-senha` são públicas; `GET /api/auth/me` exige login mas não admin. `POST /api/auth/login` rejeita com `403` (`"Este usuário deve acessar pelo login do Controle de Ligações."`) qualquer usuário com `role === 'operador_cobranca'`; `POST /api/auth/reativacao/login` faz o inverso — `403` (`"Este usuário não tem acesso ao Controle de Ligações."`) pra quem **não** é `operador_cobranca` — os dois logins são mutuamente exclusivos por role, não só por tela/URL. A gestão de usuários (`/api/admin/usuarios`, CRUD só de listar/criar/excluir — sem editar) exige além disso ser admin (`adminMiddleware`, checa `req.usuario.isAdmin`); `POST /api/admin/usuarios` aceita um campo opcional `operadorCobranca` (boolean, checagem estrita `=== true`) que grava `role = 'operador_cobranca'` em vez do default `'usuario'` — continua sem forma de criar `role='admin'`/`is_admin=1` por essa rota (admin ainda é só manual no banco). O contrato completo (payloads, status codes, mensagens de erro exatas) está em `CONTRATO-AUTH-API.md` na raiz do repo; consulte-o antes de mudar qualquer coisa relacionada a login/token/usuários. No frontend, `AuthContext.jsx` centraliza sessão/login/logout — expõe `isAdmin` e `isOperadorCobranca` (`Boolean(usuario?.role === 'operador_cobranca')`), e agora tem dois métodos de login: `login()` e `loginReativacao()` (ambos retornam o `usuario` da resposta) —, `RequireAuth.jsx`/`RequireAdmin.jsx` protegem rotas em `AppRoutes.jsx` (`RequireAuth` redireciona pra `/controle-ligacoes` quando `isOperadorCobranca`, mesmo autenticado, pra impedir um operador de chegar na casca normal do ERP por URL direta), e um 401 vindo de **qualquer** chamada de API dispara logout global + redirecionamento para `/login` (`authEvents.js`) — não implemente tratamento de 401 module a module.

**Recuperação de senha** (adendo `CONTRATO-AUTH-API-RECUPERACAO-SENHA.md`, consulte-o antes de mexer nesse fluxo): `POST /api/auth/esqueci-senha` (body `{ email }`) sempre responde `200` com a mesma mensagem genérica, exista ou não o e-mail — se existir, gera um token (`crypto.randomBytes(32)`), grava só o hash SHA-256 em `PasswordResetTokens` (`expira_em` = +1h) e envia o link `${FRONTEND_URL}/redefinir-senha?token=...` por e-mail via `brevoEmail.service.js: enviarEmailRecuperacaoSenha` (função nova, ao lado de `enviarRelatorioEmail` que o Ranking já usa — não são a mesma função). Tem rate limit próprio (`esqueciSenhaLimiter` em `app.js`, 5 tentativas/15min por IP, mesmo padrão do `loginLimiter`). `POST /api/auth/redefinir-senha` (body `{ token, novaSenha }`) valida nesta ordem: token vazio → novaSenha vazia → complexidade da senha → hash do token não encontrado/já usado/expirado (mensagem idêntica nos 3 casos, `400`); em caso de sucesso, atualiza `senha_hash`, marca o token usado e invalida (numa mesma transação) qualquer outro token não usado do mesmo usuário. A regra de complexidade (6+ caracteres, 1 maiúscula, 1 número, 1 caractere especial) vive em `backend/src/utils/senhaValidator.js` como função única (`senhaAtendeComplexidade`) — reaproveitada também em `POST /api/admin/usuarios` (Amendment ao contrato original: ganhou uma validação `400` extra de complexidade, depois de checar `email`/`senha` vazios e antes da checagem de e-mail duplicado). No frontend, `EsqueciSenhaPage.jsx` e `RedefinirSenhaPage.jsx` (`modulos/auth/`) são rotas públicas registradas direto em `AppRoutes.jsx` (fora de `RequireAuth`, **não** entram em `moduleRegistry.js` — não têm link na Sidebar, só acesso direto por URL/link de e-mail, mesmo tratamento que a tela de login já recebe); `LoginPage.jsx` ganhou o link "Esqueci minha senha" abaixo do botão "Entrar". O hint fixo de senha ("Mínimo de 6 caracteres, com pelo menos 1 letra maiúscula, 1 número e 1 caractere especial.") aparece sempre visível, não só no erro, tanto em `RedefinirSenhaPage.jsx` quanto no formulário de criar usuário em `UsuariosPage.jsx`.

**Controle de Ligações é um sub-sistema isolado, não um módulo de negócio como Ranking/Margens/Marketing** — campanha de reativação de clientes via WhatsApp, operada por um usuário com `role = 'operador_cobranca'` (rotulado "Operador de Ligações" na UI de admin). Compartilha o mesmo banco/API do resto do ERP, mas é deliberadamente invisível pro usuário comum: **não tem entrada em `moduleRegistry.js` nem link na `Sidebar`**, vive numa árvore de rotas própria em `AppRoutes.jsx` (fora de `RequireAuth`/`AppShell`), com seu próprio guard (`RequireOperadorCobranca.jsx`, espelha `RequireAdmin.jsx` mas checa `isOperadorCobranca`) e sua própria casca de layout (`ControleLigacoesShell.jsx` — sidebar/nav própria: "Início"/"Importação"/"Conversas"/"Painel de Disparo", um grupo "Configurações" que abre como **flyout lateral** [hover OU clique no botão abrem um painel `position:absolute` flutuando à direita do item, sem empurrar o resto da sidebar — substituiu um submenu vertical expansível que existia antes; revela os mesmos dois subitens, "Usuários" (só visível/acessível se `isAdmin===true`) e "Números Remetentes" (sempre visível); fecha em `mouseleave`/clique fora/seleção de item; **não abre mais sozinho** ao navegar pra uma dessas subrotas — só destaca visualmente o botão "Configurações" nesse caso], e um rodapé com `UserFooterMenu.jsx` (componente compartilhado com `Sidebar.jsx` do ERP normal, ver árvore de pastas do Frontend abaixo — e-mail do usuário antes do "@" + status estático "Disponível" + dropdown com "Sair", no lugar de um botão "Sair" bare). ## Arquitetura

### Backend: em camadas, uma pasta por camada (ainda não por módulo)

```
backend/src/
├── app.js              # App Express: middlewares globais, monta os routers /api/<modulo>, 404 + tratamento de erro
├── server.js            # ponto de entrada, carrega o .env, sobe o listener HTTP
├── config/db.js          # singleton de ConnectionPool do mssql (getPool()), lê as variáveis de ambiente DB_*
├── middlewares/
│   ├── authMiddleware.js   # valida JWT (header Authorization: Bearer <token>), popula req.usuario = { id, email, isAdmin, role }
│   ├── adminMiddleware.js  # roda depois do authMiddleware; 403 se req.usuario.isAdmin !== true
│   └── operadorCobrancaMiddleware.js  # roda depois do authMiddleware; 403 se req.usuario.role !== 'operador_cobranca'
├── routes/<modulo>.routes.js   # auth, admin, ranking, cadastros, margens, marketing, controleLigacoes
├── controllers/<modulo>.controller.js
├── services/<modulo>.service.js  # ver observação abaixo
├── models/<modulo>.model.js
├── workers/<worker>.worker.js    # ex.: envioDisparos.worker.js — iniciado direto em server.js, não por rota
└── scripts/testConnection.js
```

O fluxo de requisição segue estritamente `routes → controller → service → model`:
- **routes** — apenas mapeia verbo HTTP + caminho para uma função do controller.
- **controller** — interpreta/valida o `req`, chama o service, formata a resposta HTTP (status codes, corpo `{ "error": "..." }` em caso de falha). Sem SQL, sem lógica de negócio.
- **service** — lógica de negócio; agnóstico a framework (sem `req`/`res`), delega o acesso a dados ao model.
- **model** — a única camada que fala com o banco de dados, via o pool compartilhado do `mssql` em `config/db.js`. Toda query é parametrizada com `request.input(...)` — nunca concatene entrada do usuário em string SQL. Upserts usam `MERGE` dentro de uma transação (ver `ranking.model.js: upsertEntrada`).

Novos módulos são montados em `app.js` como `app.use('/api/<modulo>', <modulo>Routes)`, ao lado dos mounts já existentes `/api/ranking`, `/api/cadastros`, `/api/margens`, `/api/marketing`, `/api/controle-ligacoes`, `/api/auth` e `/api/admin`. Proteção de autenticação/autorização é aplicada de formas diferentes hoje, todas válidas — escolha conforme o caso: `/api/ranking`, `/api/cadastros`, `/api/margens` e `/api/marketing` recebem `authMiddleware` **no próprio mount** em `app.js` (ex.: `app.use('/api/margens', authMiddleware, margensRoutes)`, protege o router inteiro de uma vez); `/api/auth` e `/api/admin` aplicam `authMiddleware`/`adminMiddleware` **dentro do próprio router**, rota a rota, porque misturam rotas públicas (`POST /api/auth/login`) com protegidas no mesmo arquivo. Um módulo novo 100% protegido pode seguir o padrão do Ranking/Cadastros/Margens/Marketing (middleware no mount); um módulo com rotas públicas e protegidas deve seguir o padrão de `auth.routes.js`. Existe hoje um terceiro caso híbrido dentro do próprio `cadastros.routes.js` (migrado de `ranking.routes.js` — ver módulo Cadastros abaixo): a maioria das rotas herda só o `authMiddleware` do mount, mas `POST /responsaveis` e `DELETE /responsaveis/:id` aplicam `adminMiddleware` adicionalmente **na própria rota** — ou seja, mount-level auth não impede reforçar uma rota específica com uma checagem extra dentro do mesmo router. `/api/controle-ligacoes` é um quarto caso — mount-level, mas com **dois** middlewares encadeados: `app.use('/api/controle-ligacoes', authMiddleware, operadorCobrancaMiddleware, controleLigacoesRoutes)` — nenhuma rota individual do módulo precisa (nem deve) reaplicar checagem de role, o encadeamento no mount já cobre o router inteiro.

**Observação:** `.claude/agents/backend-architect.md` e `.claude/skiils/backend-conventions/SKILL.md` descrevem uma estrutura de pastas por módulo (`src/modulos/<modulo>/{controller,routes,service,model}.js`). O código atual usa, em vez disso, pastas planas `routes/`, `controllers/`, `models/`, `middlewares/`, mais um quinto tipo de pasta plana, `workers/` (hoje só `envioDisparos.worker.js`, ver "Envio de Disparos" abaixo — não é chamado por nenhuma rota, é iniciado direto em `server.js`) — `services/` existe como pasta plana também, com um arquivo por módulo (`ranking.service.js`, `auth.service.js`, `usuario.service.js`, `cadastros.service.js`, `margens.service.js`, `marketing.service.js`, `estados.service.js`, `importacao.service.js`, `disparos.service.js`, `numerosRemetentes.service.js`, `baileysSession.service.js`, `conversas.service.js`, `dashboard.service.js`) mais `brevoEmail.service.js` e `mensagensEvents.service.js` (esses dois últimos não correspondem a um módulo de rota: `brevoEmail.service.js` é acesso a serviço externo — ver seção do Brevo abaixo —, `mensagensEvents.service.js` é só um `EventEmitter` nativo do Node exportado como singleton, canal compartilhado entre o listener do Baileys e a rota SSE de Conversas — ver "Central de Mensagens" abaixo). Siga as regras de camadas (routes → controller → service → model, queries parametrizadas) independentemente de qual estrutura física de pastas você adotar; se for iniciar um novo módulo de negócio, pergunte se deve manter a estrutura plana atual ou migrar para a estrutura baseada em módulos descrita nos documentos dos agentes.

Schema de Cadastros (compartilhado — Diretor/Rede/Loja/Responsavel, já existe no banco, dono é `/api/cadastros/*`, não recrie, evolua via migrations se necessário):
- `Diretores` (id, nome, criado_em) — antes era a tabela `Redes`; perdeu `responsavel_id`/`visivel` na migração pro schema v2 (migraram para o novo nível `Redes` abaixo).
- `Redes` (id, diretor_id → FK Diretores [renomeado de `rede_id`], nome, emoji, ativo, visivel, responsavel_id → FK Responsaveis, criado_em) — antes era a tabela `Lojas`; ganhou `responsavel_id`/`visivel`, que antes viviam no nível que hoje é `Diretores`. Nível Delta/Lendários/Destemidos, filho de um Diretor.
- `Lojas` (id, rede_id → FK Redes, nome, ativo, criado_em) — loja física (ex: "SLZ 01"), consumida hoje pelos módulos Margens e Marketing (ambos via JOIN de leitura direto, sem passar por `cadastros.model.js`); o Ranking não opera nesse nível, nunca lançou/lança valor por loja física.
- `Responsaveis` (id, nome, criado_em) — vínculo (`responsavel_id`) é com `Redes`, não com `Diretores` nem `Lojas` (ver módulo Responsaveis abaixo). Na UI, o rótulo visível "Responsável" virou **"GG"** (ex.: label do `<select>`, "sem GG", título de seção "GGs") — é só texto de interface; `responsavelId`/`responsavel_id` e os nomes de função (`fetchResponsaveis`/`criarResponsavel`/`removerResponsavel`) continuam exatamente iguais.

Schema do Ranking (Categorias/Entradas, dono é `/api/ranking/*` — o resto da hierarquia antiga migrou pra Cadastros acima):
- `Categorias` (id, nome, principal, padrao, visivel, criado_em) — ganhou `padrao BIT NOT NULL DEFAULT 0` e `visivel BIT NOT NULL DEFAULT 1` (a migração que adicionou essas colunas era `MIGRATION-CATEGORIAS-PADRAO.sql`, ainda referenciado por nome em `CONTRATO-RANKING-API.md`, mas o arquivo não existe mais no repo — confirme se a migração já rodou no banco-alvo antes de presumir que essas colunas existem em um ambiente novo) para suportar o CRUD real descrito acima; as 3 categorias seed (Receita Bruta, Correção, Acessórios) têm `padrao=1`.
- `Entradas` (id, data_ref, categoria_id → FK Categorias, rede_id → FK Redes [renomeado de `loja_id`], valor, atualizado_em; UNIQUE em data_ref+categoria_id+rede_id).

Schema do Margens (dono é `/api/margens/*`):
- `MargensEntradas` (id, data_ref, loja_id → FK Lojas, faturamento, franquia, custos, cartoes, despesas, atualizado_em; UNIQUE em data_ref+loja_id) — apesar do nome das colunas, `faturamento`/`custos` guardam um **snapshot** dos valores consolidados da franquia no momento da confirmação (não um valor específico da loja); `cartoes` (mapeado como `totalTar` na API) é o Total Tar da loja, digitado direto ou derivado da margem digitada. `franquia` (mapeada como `margemInformada` na API) guarda a margem % informada manualmente quando o frontend usa o modo "margem colada" — continua `0` quando o frontend usa o modo Total Tar (campo reaproveitado sem migração de schema; é só auditoria/histórico do lançamento diário, não entra em nenhum cálculo do relatório de período). `despesas` continua sempre `0` — coluna mantida no schema mas não usada. Ver `CONTRATO-MARGENS-API.md` (v5) pro porquê desse mapeamento e a fórmula de cálculo.

Schema do Marketing (dono é `/api/marketing/*`, criado pela migration `backend/src/scripts/MIGRATION-MARKETING-ENTRADAS.sql`):
- `MarketingEntradas` (id, data_ref, loja_id → FK Lojas, faturamento_geral, faturamento_marketing, faturamento_retorno_indicacao, atualizado_em; UNIQUE em data_ref+loja_id; CHECK `>= 0` nos 3 campos de faturamento) — `data_ref` é sempre o dia 1 do mês/ano do lançamento (mesma convenção de "mês como data" do Ranking/Margens). Percentuais (`faturamentoMarketing/faturamentoGeral`, `faturamentoRetornoIndicacao/faturamentoGeral`) e a comparação subiu/caiu/igual contra o mês anterior **não são colunas** — são sempre calculados em `marketing.service.js` na leitura, nunca persistidos. Diferente de `MargensEntradas`, não há conceito de snapshot/auditoria aqui: os 3 valores gravados são sempre o que o usuário digitou, sem cópia de nenhum valor consolidado. `DELETE /api/marketing/entradas?ano=&mes=&lojaId=` (seção 3 de `CONTRATO-MARKETING-API.md`) remove o lançamento inteiro da combinação — é **idempotente** (sempre `204`, exista ou não a linha), mesmo padrão de `DELETE /api/ranking/entradas`, e não tem bloqueio de conflito (diferente das exclusões de Diretor/Rede/Loja em Cadastros).

Schema de autenticação (já existe no banco — não recrie a tabela nem insira um novo usuário admin manualmente, já existe um cadastrado):
- `Usuarios` (id, email, senha_hash, is_admin, `role` [VARCHAR(30) NOT NULL DEFAULT `'usuario'`, valores `'admin' | 'usuario' | 'operador_cobranca'` — adicionada depois de `is_admin`, os dois campos coexistem, nenhum substitui o outro], criado_em). `senha_hash` nunca é incluído em nenhuma resposta HTTP, em nenhuma rota. Não há endpoint para editar usuário nem para promover/rebaixar admin — só listar, criar (sempre `is_admin = 0`; `role = 'operador_cobranca'` se `operadorCobranca: true` no body, senão `'usuario'` — nunca `'admin'` por essa rota) e excluir; auto-exclusão é bloqueada com `409`.
- `PasswordResetTokens` (id, usuario_id → FK Usuarios, token_hash [hash SHA-256 do token, nunca texto puro], expira_em, usado [BIT, default 0], criado_em) — dono é o fluxo de recuperação de senha (`POST /api/auth/esqueci-senha`/`redefinir-senha`, ver módulo acima). Sem `UNIQUE` em `usuario_id`: um usuário pode ter vários pedidos de recuperação em aberto ao mesmo tempo. CRUD completo de Diretor/Rede/Loja (`POST/PUT/DELETE /api/cadastros/diretores`, `POST/PUT/DELETE /redes` e `POST/PUT /lojas` — Loja não tem `DELETE`, ver item abaixo) vive em `/api/cadastros/*` (migrado de `/api/ranking/*` — ver nota de migração no topo de `CONTRATO-RANKING-API.md`) e está documentado em `CONTRATO-CADASTROS-API.md`, seções 1–11. Decisões de exclusão sem cascata, testadas contra o Azure SQL local:
- **Diretor**: `DELETE` bloqueia com `409` se houver qualquer rede vinculada (`Redes.diretor_id`, mesmo inativa/oculta) — sem cascata, para não apagar histórico de `Entradas` em silêncio.
- **Rede**: `DELETE` bloqueia com `409` se houver qualquer **Loja** física vinculada (`Lojas.rede_id`, checada primeiro) **ou** qualquer `Entrada` do Ranking vinculada (`Entradas.rede_id`); a forma de "remover" uma rede com histórico é soft-delete via `PUT` com `{ ativo: false }`, reaproveitando a coluna `ativo` já existente no schema. Sem nenhum dos dois vínculos, o delete físico é permitido.
- **Loja**: **não existe rota `DELETE`** — decisão de produto, não limitação técnica (ver seção 11 de `CONTRATO-CADASTROS-API.md`). Loja nunca é excluída fisicamente, mesmo sem nenhum lançamento vinculado; a única forma de "remover" é soft-delete via `PUT /api/cadastros/lojas/:id` com `{ ativo: false }` (mesma rota aceita `nome`/`redeId` pra edição/realocação). Não implemente uma rota `DELETE` pra Loja achando que é uma omissão — é intencional.
- `DELETE /api/ranking/entradas?data=YYYY-MM-DD&categoriaId=X&redeId=Y` (seção 4 de `CONTRATO-RANKING-API.md`) remove a entrada de uma combinação pontual (data, categoria, rede) — é o que o `onBlur` do frontend chama quando o usuário zera um campo (ver acima). É **idempotente** (sempre `204`, exista ou não a linha) e, diferente de `DELETE /api/cadastros/redes/:id`/`diretores/:id` (Loja não tem rota `DELETE`, ver item acima), não tem bloqueio de conflito. Isso não muda a exclusão de **Rede**: por ser uma exclusão pontual (uma combinação por vez), uma rede com histórico em outras datas/categorias normalmente ainda terá `Entradas` vinculadas e continuará bloqueada por `409`, só podendo ser desativada via `PUT { ativo: false }` em `/api/cadastros/redes/:id`.

**Módulo Responsaveis** (seções 12–14 de `CONTRATO-CADASTROS-API.md`): pessoas responsáveis por uma rede deixaram de ser texto livre e viraram uma entidade própria. `GET/POST /api/cadastros/responsaveis` e `DELETE /api/cadastros/responsaveis/:id` fazem o CRUD (sem `PUT`/edição); `GET` roda só com o `authMiddleware` do mount, mas `POST` e `DELETE` também exigem `adminMiddleware`. `DELETE` bloqueia com `409` se qualquer `Redes.responsavel_id` ainda apontar para aquele responsável — mesma lógica sem cascata usada em Diretores/Redes/Lojas. O vínculo é com **Rede** (Delta, Lendários...), não com Diretor — na migração v1→v2 esse vínculo estava em `Diretores.responsavel_id` (quando essa tabela ainda se chamava `Redes`) e migrou junto com o rename para o novo nível `Redes`. `POST /api/cadastros/redes` não aceita o campo `responsavelId` na criação (toda rede nasce com `responsavel: null`); a atribuição é feita depois via `PUT /api/cadastros/redes/:id` com `{ responsavelId: <id> }` (ou `{ responsavelId: null }` para desatribuir). Em `GET/POST/PUT /api/cadastros/redes`, `rede.responsavel` é um objeto `{ id, nome }` ou `null` — não string. No frontend, o cabeçalho do card de cada **Diretor** em `RankingPage.jsx` mostra só `diretor.nome` puro (Diretor não tem campo `responsavel`/GG); o responsável (rotulado "GG" na UI) aparece em cada **linha de Rede**, dentro do card do Ranking e na `ConfigView` — comportamento intencional, não é bug.

**Módulo Margens** (`/api/margens/*`, documentado em `CONTRATO-MARGENS-API.md` v5): dono só da tabela `MargensEntradas` — não duplica CRUD de Loja/Rede/Diretor/Responsavel (isso é do módulo Cadastros); `margens.model.js` faz suas próprias queries de JOIN de **leitura** direto contra `Lojas`/`Redes`/`Diretores`/`Responsaveis` (não chama `cadastros.model.js`) só pra montar o relatório agrupado e validar a existência de `lojaId` no upsert. `POST /api/margens/entradas` faz upsert (`MERGE`) por `(data, lojaId)`, gravando `custos=custoProduto`/`cartoes=totalTar`/`despesas=0` e `franquia=margemInformada` — campo opcional no corpo do request (`margemInformada`, número finito, sem limite inferior); ausente ou `null` grava `0`, mesmo comportamento retrocompatível de antes desse campo existir (ver schema de `MargensEntradas` acima e a pegadinha do snapshot documentada na Visão Geral).

**Módulo Marketing** (`/api/marketing/*`, documentado em `CONTRATO-MARKETING-API.md` v1): dono só da tabela `MarketingEntradas` — igual ao Margens, não duplica CRUD de Loja/Rede/Diretor (isso é do módulo Cadastros); `marketing.model.js` faz suas próprias queries de JOIN de **leitura** direto contra `Lojas`/`Redes`/`Diretores` (não chama `cadastros.model.js`) pra montar a listagem agrupada e validar a existência de `lojaId` no upsert. `GET /api/marketing/entradas` filtra `Redes.ativo = 1` **e** `Lojas.ativo = 1` na própria query (Diretor não tem coluna `ativo`, some naturalmente da árvore quando não tem nenhuma rede vinculada — `DELETE /api/cadastros/diretores/:id` já bloqueia exclusão com rede vinculada); `visivel` não é filtrado, esse conceito é só do grid do Ranking. `POST /api/marketing/entradas` faz upsert (`MERGE`) por `(dataRef, lojaId)` com os 3 campos de faturamento sempre obrigatórios (`400` se algum estiver ausente/negativo, nesta ordem: `lojaId` → `ano`/`mes` → `faturamentoGeral` → `faturamentoMarketing` → `faturamentoRetornoIndicacao`); `DELETE /api/marketing/entradas` (ver schema acima) reaproveita a mesma conversão `(ano, mes) → dataRef` (`formatDataRef` em `marketing.service.js`) que o POST já usa, sem duplicar essa lógica.

**Módulo Controle de Ligações** (`/api/controle-ligacoes/*`, documentado em `CONTRATO-CONTROLE-LIGACOES-API.md` v2 DRAFT + adendos v3–v7 — ver visão geral do sub-sistema mais acima): rotas `GET/POST /estados`, `GET/POST /numeros-remetentes` + `PUT/DELETE /numeros-remetentes/:id`, `GET /numeros-remetentes/:id/conexao/stream` (SSE) + `POST /numeros-remetentes/:id/conexao/desconectar` (Conexão Baileys, v5 — ver abaixo), `POST /contatos/importar` (multipart), `GET /contatos/importar/historico`, `GET /contatos/importar/:loteId`, `GET /painel-disparo`, `GET /estados/:estadoId/contatos-disponiveis`, `POST /disparos/verificar` + `POST /disparos` (Painel de Disparo, split v4 — ver abaixo), `GET /disparos/:id` (Envio de Disparos, v6 — ver abaixo) e `GET/POST /conversas` (`GET` aceita `busca`/`apenasNaoLidas` e, desde o adendo Pipeline, também `numeroRemetenteId`/`status`, todos opcionais — ver "Pipeline" abaixo), `GET /conversas/stream` (SSE), `GET/POST /conversas/:contatoId/:numeroRemetenteId/mensagens` (o segmento `:numeroRemetenteId` é uma mudança de rota posterior à v7 original — ver "Central de Mensagens" abaixo), `GET /notificacoes` (Central de Mensagens, v7 — ver abaixo), `PUT /conversas/:contatoId/:numeroRemetenteId/status` (Status de Conversa, adendo posterior à v7 — ver abaixo), `GET /pipeline` e `GET /pipeline/:contatoId/:numeroRemetenteId/historico` (Pipeline, adendo posterior à v7 — ver abaixo), `GET /dashboard` (Dashboard, adendo posterior à v7, também com `dataInicio`/`dataFim` desde o adendo Pipeline — ver abaixo) e `GET /aguardando-acao` (card "Aguardando Ação", NÃO faz parte de `getDashboard`/não aceita `estadoId`/período — ver "Dashboard" abaixo) — todas já protegidas no mount de `app.js` (`authMiddleware` + `operadorCobrancaMiddleware`), sem checagem própria em nenhuma rota individual. O router (`controleLigacoes.routes.js`) também tem um middleware próprio no topo, `Cache-Control: no-store` + remoção de `If-None-Match`/`If-Modified-Since` da request — Express gera ETag (`weak`) por padrão pra toda resposta JSON, e sem essa correção o cliente podia receber `304 Not Modified` de corpo vazio em vez do dado atualizado; **esse fix hoje só existe neste módulo** — `/api/ranking`, `/api/margens`, `/api/marketing`, `/api/cadastros`, `/api/auth`/`/api/admin` continuam sujeitas ao mesmo comportamento de ETag/304 do Express, sem correção (ver "Segurança de borda" abaixo). Upload usa `multer` (`memoryStorage()`, campo `arquivo`, limite 10MB, só `.xlsx`/`.csv`) + **`exceljs`** pra ler a planilha — não `xlsx`/SheetJS, que não está instalado no projeto; ambas são dependências novas em `backend/package.json`. `POST /contatos/importar` lê a primeira planilha, acha as colunas `NOME`/`CONTATO` no cabeçalho (case-insensitive), normaliza telefone (só dígitos), extrai o DDD (posições 3-4, logo depois do `55`, só se o total tiver 12-13 dígitos), rejeita linha sem nome ou sem DDD extraível e linha cujo telefone normalizado já existe em `Contatos` — inclusive duplicata dentro do próprio arquivo (o registro existente sempre vence, nunca é sobrescrito) —, agrupa o resto por Estado via `EstadoDDDs` e insere tudo em `Contatos` com `numero_remetente_id = NULL`, numa única transação junto com a linha de `LotesImportacao`. **A partir da v3**, cada linha rejeitada (erro de formato ou duplicidade) também grava uma linha em `LoteImportacaoErros` (número da linha 1-indexed contando o cabeçalho, motivo, e `contato_existente_id` quando aplicável) — consultável depois via `GET /contatos/importar/:loteId` (resumo + `porEstado` + `erros[]`) ou `GET /contatos/importar/historico` (lista todos os lotes, não só os antigos "pendentes"). **`POST /contatos/importar/:loteId/confirmar` foi descontinuada na v3** — a rota continua montada, mas sempre responde `410 Gone` (`{ "error": "Rota descontinuada. A escolha de número acontece no Painel de Disparo." }`), pra dar um erro claro em vez de um `404` genérico pra qualquer cliente antigo que ainda a chame; não existe mais nenhuma etapa de confirmação/escolha de número na importação. Não existe tela/rota própria de CRUD de Estado — a criação acontece embutida no modal de Número Remetente (`NumerosRemetentesPage.jsx`, mini-formulário "Cadastrar novo estado"), não numa tela separada.

**Painel de Disparo** (`PainelDisparoPage.jsx`, rotas 12–14 do adendo v3 do contrato, mais o split v4) — onde a Lívia seleciona manualmente até 10 contatos por vez, por Estado, e registra a intenção de disparo (grava a fila que o worker de "Envio de Disparos", abaixo, consome de fato). Decisão de design central: um contato pertence a um Estado (fixo, definido na importação) mas **nunca fica travado a um número remetente específico** — em disparos diferentes, o mesmo contato pode ser contatado por qualquer número ativo do seu Estado; a fila de `GET /estados/:estadoId/contatos-disponiveis` é filtrada só por `estado_id`, nunca por `numero_remetente_id`. `GET /painel-disparo` devolve, por Estado (inclusive Estado sem número ativo ou sem contato, pra o frontend renderizar o card vazio), a contagem de contatos e os `NumerosRemetentes` ativos; a escolha de número na tela não filtra a lista de contatos abaixo, só define qual número vai ser usado *nesse* disparo. **A partir do adendo v4, criar um disparo virou um fluxo em duas chamadas reais, não uma só**: `POST /disparos/verificar` roda as mesmas validações de `POST /disparos` (nesta ordem: `contatoIds` presente/≤10, `numeroRemetenteId` ativo e do Estado certo, todo `contatoId` pertencente ao Estado informado) mas **não grava nada** — só devolve `{ avisos: [{contatoId,nome,telefone}] }` com os contatos que já tinham `disparadoUltimos3Dias=true`; `POST /disparos` (mesmas validações, mesmas mensagens de erro) sempre grava de verdade quando chamado — 1 linha em `Disparos` + N em `DisparoContatos` numa transação — e devolve só `{ disparoId, totalContatos }`, **sem `avisos`** (isso deixou de ser responsabilidade dessa rota). O motivo da separação: antes, `POST /disparos` já gravava na mesma chamada que devolvia os avisos, dando a falsa impressão de que ainda dava pra cancelar depois de ver o aviso. No frontend, `PainelDisparoPage.jsx` reflete esse fluxo: clique em "Disparar" chama `verificar` primeiro; se `avisos` vier vazio, chama `POST /disparos` automaticamente em seguida (um clique só, igual antes); se vier não-vazio, abre um modal "Aviso antes de disparar" com "Cancelar" (nada é gravado, seleção do usuário permanece intacta) e "Disparar mesmo assim" (só aí chama `POST /disparos` de verdade). Qualquer caminho que efetive o disparo com sucesso rechama `GET /estados/:estadoId/contatos-disponiveis` daquele card em paralelo, pra badge "Contatado há menos de 3 dias" atualizar sem precisar recarregar a página. Em ambas as rotas, os avisos **nunca bloqueiam** nada — são só informativos, recalculados no servidor a cada chamada, nunca confiando no que o cliente mandou.

**Validação de elegibilidade do número remetente (adendo posterior à v4, mesmas rotas)**: `POST /disparos` e `POST /disparos/verificar` (ambas via a mesma função compartilhada, `disparos.model.js: validarNumeroEContatos`, pra não duplicar a lógica entre as duas) também recusam com `400` um `numeroRemetenteId` que exista/pertença ao Estado/esteja `ativo` mas não esteja pronto pra disparar de verdade — checado ANTES da validação de `contatoIds` e antes de qualquer gravação: `status_conexao != 'conectado'` (`"Este número não está conectado ao WhatsApp. Conecte-o em Configurações antes de disparar."`) ou `nome_colaboradora` `NULL`/vazio/só espaços (`"Este número não tem nome da colaboradora configurado. Preencha em Configurações antes de disparar."`). Motivo: antes dessa validação, `POST /disparos` respondia `201` mesmo para um número fadado a falhar, e o operador só descobria minutos depois pelo worker de "Envio de Disparos" — agora o erro aparece na hora. No frontend, `PainelDisparoPage.jsx` antecipa essa checagem pra UX (não só trata o `400`): busca `GET /numeros-remetentes` (que já tem `statusConexao`/`nomeColaboradora`, diferente de `GET /painel-disparo`, que só devolve `statusConexao`) uma vez por página e cruza com os `numerosAtivos` de cada card; no `<select>`, opções não elegíveis ficam `disabled` com um sufixo ("(desconectado)" ou "(sem colaboradora configurada)", prioridade pro motivo de desconexão quando os dois faltam); se nenhum número do Estado for elegível, o botão "Disparar" fica desabilitado com um aviso abaixo do seletor; quando o número selecionado É elegível, aparece uma caixa (mesmo estilo visual do aviso, tom `--success`/`--success-bg`) com `📱 {numero} · Atendido por {nomeColaboradora}`. Isso é só antecipação de UX — o `400` do backend continua sendo a fonte de verdade final (ex.: dado desatualizado no frontend, número que desconectou entre o carregamento da página e o clique em "Disparar").

**Conexão Baileys** (adendo v5 do contrato — primeira metade da integração WhatsApp: conectar um número remetente de verdade) — Baileys roda no **mesmo processo** do backend Node (sem microsserviço separado), gerenciado por `backend/src/services/baileysSession.service.js`: um `Map` em memória de `numeroRemetenteId → sessão` (socket Baileys ativo, listeners SSE, timers, tentativas de reconexão), sessão de cada número persistida em disco via `useMultiFileAuthState` em `backend/sessions/baileys/{numeroRemetenteId}/` (pasta inteira no `.gitignore` — credenciais sensíveis, nunca versionadas). `GET /numeros-remetentes/:id/conexao/stream` abre (ou reaproveita, se já em memória) a sessão e transmite por Server-Sent Events: `event: qr` (`{qr}`, string crua — o frontend renderiza client-side com `qrcode.react`, o backend nunca gera imagem), `event: conectado` (`{numero}`, banco já atualizado antes do evento), `event: erro`, `event: ja_conectado` (quando `:id` já estava `'conectado'`, nenhum QR novo é aberto); o stream é encerrado pelo servidor logo após um desses três. Múltiplas abas/streams simultâneos pro mesmo `:id` reaproveitam o mesmo socket (broadcast dos eventos), e fechar uma aba antes do QR ser escaneado remove só aquele listener, não a sessão. `POST /numeros-remetentes/:id/conexao/desconectar` faz logout + apaga a pasta de sessão + grava `numero=NULL`/`status_conexao='aguardando_conexao'`. Reconexão automática (até 3 tentativas, backoff `tentativa*2000ms`) só se aplica a uma sessão que já chegou a ficar `'conectado'` e caiu inesperadamente; esgotadas as tentativas, vira `'desconectado'` (diferente de `'aguardando_conexao'`, reservado pra quando nunca houve conexão ou foi encerrada de propósito). **Reconciliação no boot** (`reconciliarSessoesNoBoot`, chamada de `server.js` em paralelo ao `app.listen`, não bloqueia o processo subir): se o processo reiniciar com algum `NumerosRemetentes.status_conexao='conectado'` no banco, o `Map` em memória se perdeu mas o banco ainda diz `'conectado'` — a rotina busca todos esses números e tenta restaurar cada um a partir da pasta de credenciais em disco, **em sequência** (nunca em paralelo), marcando `'desconectado'`/`numero=NULL` e limpando a pasta órfã pra quem falhar (credencial inválida, pasta ausente, timeout); o efeito não é instantâneo, um número pode aparecer brevemente ainda `'conectado'` logo após o boot. No frontend, `NumerosRemetentesPage.jsx` ganhou um modal de conexão (QR com fundo claro sobre o tema escuro) e o botão "Conectar WhatsApp"/"Desconectar" conforme `statusConexao` — como o `EventSource` nativo do browser não permite enviar o header `Authorization` que a API exige, o stream é consumido via `fetch` + leitura manual do corpo (`response.body.getReader()`/`TextDecoder`, parsing manual do formato SSE) em `abrirStreamConexao` (`controleLigacoesConfigApi.js`), não via `new EventSource(...)`.

**Envio de Disparos** (adendo v6 do contrato — segunda metade da integração WhatsApp: o worker que de fato manda a primeira mensagem) — `backend/src/workers/envioDisparos.worker.js`, um `setInterval` dentro do próprio processo backend (iniciado a partir de `server.js`, junto da reconciliação de boot), intervalo configurável via `ENVIO_DISPAROS_INTERVALO_MS` (default 15000ms). A cada ciclo, busca até `ENVIO_DISPAROS_LOTE_TAMANHO` (default 5) linhas de `DisparoContatos` com `status='pendente'` e processa **em sequência** (nunca em paralelo), com um delay (`ENVIO_DISPAROS_DELAY_ENTRE_MENSAGENS_MS`, default 4000ms) entre envios reais — mitigação de risco de ban, não só performance. Por contato: se o `numero_remetente_id` não tiver sessão Baileys `'conectado'` em memória (`baileysSession.obterSocketConectado`) ou `nome_colaboradora` estiver vazio, marca `status='falha'` sem consumir a rotação de template; senão, calcula o próximo template ativo em `MensagensTemplates` (round-robin por `ordem`, ciclando de volta ao primeiro, ponteiro em `ConfiguracoesEnvio.ultimo_template_usado_id`, lógica isolada em `backend/src/models/mensagensTemplates.model.js`) **sem persistir ainda** (a leitura fica fora de qualquer transação que segure lock durante a chamada de rede ao Baileys), monta a mensagem substituindo `{nomeColaboradora}` e obtém o socket Baileys ativo. **Antes de enviar, chama `sock.onWhatsApp(telefone)`** (bugfix — o número armazenado em `Contatos.telefone` pode não bater com a variante que o WhatsApp tem registrada, sobretudo em número brasileiro por causa do 9º dígito do celular; sem essa checagem, `sock.sendMessage` podia "suceder" — sem lançar exceção — sem a mensagem chegar a ninguém, e o worker gravava `status='enviado'` mesmo assim): se `onWhatsApp` não confirmar uma conta real (retorno vazio ou sem `exists`) ou lançar erro, marca `status='falha'` (`erro='Número não possui WhatsApp ativo ou não pôde ser verificado.'`, ou a mensagem do erro de verificação) **sem chamar `sendMessage`** e sem avançar a rotação — mas conta como tentativa real (`tentouEnviar: true`, aplica o delay entre mensagens do próximo item do lote, já que consultou a rede). Só quando `onWhatsApp` confirma, o worker usa o `jid` que ele retornou (não o `${telefone}@s.whatsapp.net` concatenado manualmente — pode ser diferente) para `sock.sendMessage(jid, {text})`; só em caso de sucesso é que `DisparoContatos` (`status='enviado'`, `template_usado_id`, `mensagem_enviada`, `enviado_em`) e `ConfiguracoesEnvio.ultimo_template_usado_id` são gravados juntos, numa transação curta — falha no envio (do `sendMessage` em si) grava só `status='falha'`/`erro` em `DisparoContatos`, **sem retry automático** e **sem avançar a rotação**. `GET /api/controle-ligacoes/disparos/:id` (protegida como o resto do módulo) devolve o disparo com estado/número remetente e a lista de contatos com `status`/`mensagemEnviada`/`enviadoEm`/`erro` de cada um, pra acompanhar o progresso. **Lacuna conhecida**: não existe tela/rota de CRUD pra `MensagensTemplates` — hoje só populável via `INSERT` direto no banco; sem isso, todo `DisparoContatos` pendente vira `falha` com `"Nenhum template de mensagem ativo cadastrado."`. `NumerosRemetentes.nome_colaboradora`, por sua vez, já é editável via `PUT /numeros-remetentes/:id` (ver schema acima).

**Central de Mensagens** (adendo v7 do contrato — inbox de mensagens recebidas de clientes via WhatsApp, `ConversasPage.jsx` no shell do Controle de Ligações) — um listener `sock.ev.on('messages.upsert', ...)` registrado dentro de `iniciarSocket` (mesmo lugar que já cobre reconexão/restauração de boot, sem duplicar código) chama `handleMessagesUpsert` em `baileysSession.service.js`; só processa `type === 'notify'` (ignora `'append'`, emitido durante sincronização de histórico — sobretudo na reconciliação de boot, senão inundaria `Mensagens` com histórico antigo a cada restart). **`key.fromMe === true` NÃO é mais ignorado** (mudança posterior à v7 original) — confirmado por teste real que o Baileys nunca emite `messages.upsert`/`type:'notify'` pro que o próprio socket do backend acabou de enviar via `sock.sendMessage` (worker de disparo/resposta manual), então todo `fromMe===true` que chega neste listener é sempre uma mensagem que o atendente mandou manualmente pelo próprio celular; `handleMessagesUpsert` captura `const ehDoAtendente = msg?.key?.fromMe === true` e deixa a mensagem seguir o fluxo normal, gravando com `remetente: ehDoAtendente ? 'atendente' : 'cliente'` e forçando `ePrimeiraRespostaCliente=false` sem chamar `existeMensagemClienteAnterior` quando `ehDoAtendente` (não faz sentido essa checagem pra mensagem que não é do cliente). **Resolução de telefone tem duas camadas de bugfix** (`resolverTelefoneDoRemetente`): (1) o WhatsApp moderno frequentemente endereça o remetente por um LID (`remoteJid` terminando em `@lid`, um id interno de ~15 dígitos que NÃO é telefone) em vez de `@s.whatsapp.net` — resolvido tentando `msgKey.remoteJidAlt` e depois `sock.signalRepository.lidMapping.getPNForLID(...)`, e só desistindo (log de "LID não resolvido") se nenhum dos dois resolver; (2) mesmo com o telefone certo, o servidor do WhatsApp às vezes representa a conta SEM o 9º dígito do celular brasileiro (formato pré-2012) mesmo quando o número de discagem real inclui o 9 — `gerarVariantesTelefoneBr(telefone)` gera a variante com/sem o 9º dígito (formato `55`+DDD+número, 12↔13 caracteres) e `mensagens.model.js: findContatoIdPorTelefoneComVariantes` busca por todas as variantes numa única query `WHERE telefone IN (...)` antes de desistir (log de "telefone sem Contato correspondente" — causa diferente de LID não resolvido, logs distintos de propósito). **Extração de texto desembrulha envelopes antes de checar `conversation`/`extendedTextMessage.text`** (mudança posterior à v7 original, bugfix de mensagens somem sem rastro): `desembrulharMensagem` (função pura, exportada de `baileysSession.service.js`) desembrulha recursivamente (até 5 níveis) `ephemeralMessage`/`viewOnceMessage`/`viewOnceMessageV2` — sem isso, uma conversa com mensagens temporárias/efêmeras ativadas no WhatsApp nunca batia com `conversation`/`extendedTextMessage` na raiz. `protocolMessage` (edição/revogação de mensagem existente) é ignorado deliberadamente com log explícito, sem gravar linha nenhuma em `Mensagens` — decisão de escopo, não uma lacuna silenciosa. Mensagem de mídia (áudio, imagem, etc.) — ou qualquer tipo não reconhecido depois de desembrulhar — vira o mesmo placeholder de texto fixo (`MENSAGEM_MIDIA_PLACEHOLDER`), com um log de DEBUG das chaves de nível superior do `message` não reconhecido, pra facilitar identificar o próximo tipo não coberto. **Cada mensagem do array `upsert.messages` é processada dentro do seu próprio `try/catch`** — antes só existia um `.catch()` de nível de BATCH (`sock.ev.on('messages.upsert', ...)`), então uma exceção ao processar UMA mensagem abortava o resto do lote inteiro sem log específico (causa raiz confirmada do "sumiço silencioso" que motivou essas correções); o try/catch por mensagem garante que uma falha isolada não impede o processamento das mensagens seguintes do mesmo lote. Dedup de evento duplicado do Baileys é via captura do erro de violação do índice único filtrado `UQ_Mensagens_baileysId` (ver schema acima), não uma checagem prévia — mais simples, sem condição de corrida.

**Sino de notificações (handoff IA→humano)**: `Mensagens.e_primeira_resposta_cliente` marca a mensagem que é a PRIMEIRA de um contato desde sempre — antes de inserir, `handleMessagesUpsert` chama `mensagensModel.existeMensagemClienteAnterior(contatoId, numeroRemetenteId)` (2 parâmetros desde a mudança pra threads separadas por [contato, número]; ordem importa: checagem acontece ANTES do insert desta mensagem) pra derivar esse flag — só quando a mensagem NÃO é do atendente (`ehDoAtendente===false`, ver "Central de Mensagens" acima); pra mensagem do atendente, `ePrimeiraRespostaCliente` é sempre forçado `false` sem chamar essa função. `GET /api/controle-ligacoes/notificacoes` devolve `{ naoVistas: N, itens: [...] }` — `naoVistas` é a contagem de `Mensagens` com `e_primeira_resposta_cliente=1 AND lida=0` (`mensagens.model.js: contarNotificacoesNaoVistas`); `itens` (campo aditivo, quem já lia só `naoVistas` continua funcionando) é a lista das até 10 notificações pendentes mais recentes (mesmo filtro, `ORDER BY criado_em DESC`, `mensagens.model.js: listNotificacoesPendentes`), cada uma `{ contatoId, numeroRemetenteId, nomeContato, telefone, preview, criado_em }` — `numeroRemetenteId` é campo novo (mudança posterior à v7 original), necessário pro clique numa notificação conseguir pré-selecionar a thread certa em `ConversasPage.jsx` sem depender da lista de `GET /conversas` já estar carregada (ver Visão Geral); `preview` é o `corpo` da mensagem truncado em 80 caracteres com "…" quando corta (`criado_em` fica em snake_case de propósito, mesmo padrão já usado por `GET /conversas/:contatoId/:numeroRemetenteId/mensagens` pra timestamp de mensagem, não é inconsistência). `lida` é zerada pro badge quando o operador abre a conversa (efeito colateral já existente de `GET /conversas/:contatoId/:numeroRemetenteId/mensagens`, que marca `lida=1` em toda mensagem de cliente não lida daquela thread). No frontend, o sino 🔔 (badge numérico, `"9+"` a partir de 10, `position:fixed` no canto superior direito da tela — ver acima) mora em `ControleLigacoesShell.jsx` — busca `naoVistas`+`itens` ao montar (`refetchNotificacoes`), mantém sua PRÓPRIA conexão SSE (independente da de `ConversasPage.jsx`, porque o sino precisa contar mesmo fora da tela de Conversas) que, a cada evento SSE com `primeiraResposta:true`, chama `refetchNotificacoes()` de novo (refetch completo de `naoVistas`+`itens` — **não** um incremento local isolado do contador; um incremento otimista só do número deixava o badge certo mas a lista do dropdown presa no estado da montagem inicial, bug já corrigido) e expõe a mesma `refetchNotificacoes` via `<Outlet context={{refetchNotificacoes}}/>` pra `ConversasPage.jsx` (via `useOutletContext()`) recalcular sempre que uma conversa é aberta/marcada como lida. `notificacoesItens` no estado do componente distingue `null` ("Carregando...", ainda não buscou) de `[]` ("Nenhuma notificação.", buscou e veio vazio de verdade) — importante pra não piscar a mensagem de vazio antes do primeiro fetch resolver.

**Tempo real via SSE, sem biblioteca nova**: `GET /conversas/stream` reaproveita o mesmo formato de evento (`event: <nome>\ndata: <json>\n\n`, `res.write`/`res.flushHeaders?.()`) e o mesmo padrão de consumo no frontend (`fetch`+`response.body.getReader()`/`TextDecoder`, parsing manual — nunca `new EventSource(...)`, que não permite mandar o header `Authorization` exigido) já estabelecidos pela Conexão Baileys — mas com uma diferença deliberada: o stream de Conversas NÃO se encerra sozinho depois de emitir um evento (a tela de Conversas fica aberta indefinidamente), só fecha quando o cliente desconecta (`req.on('close', ...)`). Produtor: `mensagensEvents.service.js` (`EventEmitter` singleton) recebe `emit('mensagem-recebida', {contatoId, numeroRemetenteId, primeiraResposta})` de `handleMessagesUpsert` só quando a mensagem é de fato inserida (não em dedup); o controller do stream repassa isso tal como veio, como `event: nova-mensagem`. O mesmo stream também repassa um segundo tipo de evento, `event: status-atualizado` (`{contatoId, numeroRemetenteId, baileysMessageId, status}`), produzido por `handleMessagesUpdate` (ver `Mensagens.status_entrega` no schema acima) sempre que o WhatsApp confirma avanço de entrega de uma mensagem já enviada — mesmo `EventEmitter`, mesmo padrão de listener no controller (`mensagensEventsService.on('mensagem-status-atualizada', ...)`), só um segundo tipo de evento multiplexado no mesmo canal. Broadcast automático pra múltiplos clientes/abas conectados simultaneamente é de graça, via o próprio `EventEmitter` — não guarda histórico de eventos, quem conecta depois de um evento simplesmente não o recebe (a tela sempre faz um fetch REST inicial, o SSE é só push incremental).

**Mudança de modelo (posterior à v7 original): cada combinação (contato, número remetente) é uma thread separada, não mais "1 conversa por contato".** `mensagens.model.js: listConversas` foi reescrita pra agrupar por `(contato_id, numero_remetente_id)` — a query principal virou uma CTE (`GROUP BY c.id, ..., m.numero_remetente_id, n.apelido`) com um `CROSS APPLY` pra pegar a última mensagem de cada thread, em vez do antigo `GROUP BY` só por contato + duas queries em lote separadas (`MAX(id)`/`MIN(id)`) pra achar número "atual" vs "inicial". Como consequência, `numeroRemetenteAtual` e `numeroRemetenteInicial` que `GET /conversas` devolve **são sempre o mesmo valor agora** (não podem mais divergir — o campo duplicado foi mantido de propósito só pra não quebrar o frontend, que já esperava os dois campos separados; não é redundância acidental). Na lista (coluna esquerda de `ConversasPage.jsx`), cada item mostra o `numeroRemetenteInicial` como uma pill roxa em destaque (`bg-[var(--violet)]/20`, negrito, sem o prefixo "via" — mudança posterior à v7 original; antes era um chip discreto com borda neutra e o texto "via {apelido}", trocado pra ficar visualmente diferente da tag de status neutra que fica ao lado, ver "Status de Conversa" abaixo); a chave de cada `<li>` combina `contato.id`+`numeroRemetenteAtual.id` (não só `contato.id`), já que o mesmo contato pode aparecer em múltiplas linhas, uma por thread. **`GET /conversas/:contatoId/:numeroRemetenteId/mensagens`** (rota ganhou o segmento `:numeroRemetenteId` — era só `:contatoId`) devolve o histórico só daquela thread: `{ mensagens: [...] }` — `numeroRemetenteInicial` saiu de vez da resposta (antes era `{id,apelido}|null`; como a thread já é escopada pelos dois ids, o número é sempre o mesmo do início ao fim, então virou redundante) e `numeroRemetenteAtual` continua não vindo nessa rota (o frontend já tem esse dado na lista `conversas` já carregada). No cabeçalho do chat aberto, `formatOrigemAtendimento` foi simplificada pra sempre `"Atendido por: {apelido}"` (usando só `numeroRemetenteAtual` da thread selecionada) — o caso antigo "Iniciado por: X • Respondendo por: Y" não existe mais, porque uma thread nunca troca de número. `POST /conversas/:contatoId/:numeroRemetenteId/mensagens` (resposta manual, `remetente='colaboradora'`) usa o número remetente informado na própria rota (a thread sendo respondida) — não mais "o último número que respondeu" (`findUltimoNumeroRemetenteDaConversa`, função que ficou sem uso, mantida no model mas não chamada por nenhuma rota); valida que a thread já tem histórico via `mensagensModel.existeMensagemNaThread(contatoId, numeroRemetenteId)` (nova, substituiu a busca por "última mensagem") antes de checar se o número está conectado; reaplica a mesma checagem `sock.onWhatsApp(telefone)` do worker de envio antes de mandar, pelo mesmo motivo (telefone salvo pode não bater com a variante que o WhatsApp tem registrada). O clique numa conversa da lista (`selecionarConversa`, `ConversasPage.jsx`) monta `contatoSelecionado` incluindo `numeroRemetenteId: conversa.numeroRemetenteAtual.id`; trocar entre duas threads do mesmo contato (ex.: "via Bruno" → "via Livia") sempre recarrega as mensagens porque `selecionarConversa` não tem guarda de "já selecionado", e o destaque visual (`selecionada`) compara `contatoId` **e** `numeroRemetenteId`, não só o contato.

**Status de Conversa** (adendo posterior à v7, ver seção "Status de Conversa" em `CONTRATO-CONTROLE-LIGACOES-API.md`) — cada thread (contato + número remetente) pode ter um resultado comercial atribuído manualmente pelo operador: `atendeu`/`agendou`/`nao_atendeu`/`venda`/`perdido` (ver schema `ConversasStatus` acima). `PUT /api/controle-ligacoes/conversas/:contatoId/:numeroRemetenteId/status` (`conversas.controller.js: atualizarStatus`, valida `contatoId`/`numeroRemetenteId` como inteiros positivos e `status` contra o enum antes de chamar `conversasService.atualizarStatus` → `mensagensModel.upsertStatusConversa`, um `MERGE` por `(contato_id, numero_remetente_id)`) é a única forma de setar/trocar o status — não existe progressão forçada nem máquina de estados, o operador pode pular direto pra `venda` sem nunca ter marcado `agendou`. `GET /conversas` (`listConversas`) ganhou um `LEFT JOIN ConversasStatus` e devolve `status: string|null` por thread. No frontend, `ConversasPage.jsx` mostra o status como uma tag colorida (`STATUS_CORES`/`corStatus`, cores fixas por status reaproveitando variáveis de tema já existentes — `--teal` atendeu, `--violet` agendou, `--warning` não atendeu, `--success` venda, `--danger` perdido) tanto na lista (`ConversaItem`) quanto num `<select>` no cabeçalho da thread aberta (`STATUS_CONVERSA_OPCOES`, com uma opção neutra "Sem status" pra `null`); trocar o select chama o `PUT` e atualiza `conversas` local via `setConversas`, sem refetch completo.

**Pipeline** (`PipelinePage.jsx`, `frontend/src/modulos/controle-ligacoes/pipeline/`, adendo posterior à v7, item de nav "Pipeline" entre "Conversas" e "Painel de Disparo" no `ControleLigacoesShell.jsx`) — visão kanban das threads que já têm `status` em `ConversasStatus`, 5 colunas fixas na ordem Atendeu/Agendou/Não atendeu/Venda/Perdido. `GET /api/controle-ligacoes/pipeline` (`conversas.controller.js: pipeline` → `conversasService.listarPipeline` → `mensagens.model.js: listPipeline`) devolve um array **flat** sem envelope, snake_case sem transformação, EXCETO `motivoDetalhe` (renomeado de `motivo_detalhe` no `.map()` final da função — os demais campos passam direto): `{ contato_id, nome, telefone, numero_remetente_id, apelido, status, atualizado_em, motivo, motivoDetalhe }` — `motivo`/`motivoDetalhe` (adendo "motivo de perda", ver abaixo) vêm de um `OUTER APPLY` que busca a linha mais recente de `StatusHistorico` com `status_novo='perdido'` daquela thread, `null` pra qualquer status que não seja `'perdido'` (ou pra uma thread que nunca foi perdido). Sempre filtra `status IS NOT NULL`; aceita `busca` (LIKE contra `Contatos.nome`), `numeroRemetenteId` (inteiro positivo), `statusInicio`/`statusFim` (`YYYY-MM-DD`, contra `ConversasStatus.atualizado_em` — **renomeados de `dataInicio`/`dataFim`, rename e não alias, os nomes antigos não são mais aceitos**) e `disparoInicio`/`disparoFim` (novo par, `YYYY-MM-DD`, contra `Disparos.criado_em` — via `EXISTS` contra `DisparoContatos`/`Disparos`, não `JOIN` direto, pra não duplicar linha quando o contato tem mais de um `Disparo`), todos opcionais e sempre bindados via `.input(...)` mesmo ausentes (padrão `@param IS NULL OR ...`, diferente do fragmento condicional em JS que `listConversas` usa). No frontend, `PipelinePage.jsx` tem DOIS `DateRangeFilter` lado a lado na barra de filtros, rotulados "Data da mudança de status" (statusInicio/Fim) e "Data do disparo" (disparoInicio/Fim), cada um com seu próprio par de estado — botão "Limpar" reseta os 6 filtros (busca, atendente, os 4 de data) de uma vez. `GET /conversas` ganhou `numeroRemetenteId`/`status` na mesma leva: `numeroRemetenteId` filtra dentro da CTE `ThreadsBase` (o campo já está disponível ali), `status` filtra numa cláusula `WHERE` nova na query externa, depois do `LEFT JOIN ConversasStatus` — não pode ir dentro da CTE, `cs` não existe lá.

**`'atendeu'` não é selecionável manualmente em nenhum `<select>` de TROCA de status** (só é atribuído pelo sistema, via `marcarAtendeuSeVazio`) — a opção continua visível (pra mostrar corretamente quando já É o status atual), só fica `disabled` no `<option>`, tanto no `<select>` de status de uma thread aberta em `ConversasPage.jsx` (`STATUS_CONVERSA_OPCOES`) quanto no `<select>` de cada card em `PipelinePage.jsx` (`COLUNAS`). Isso é diferente do `<select>` de **filtro** por status que `ConversasPage.jsx` ganhou na mesma leva (barra de pills acima da lista, ao lado de um filtro de atendente e um toggle "Ocultar vendas" 100% client-side) — ali `'atendeu'` continua totalmente selecionável, filtrar por ele é válido, só a troca manual é bloqueada.

**Motivo de perda** (adendo posterior ao Pipeline) — toda vez que uma thread é marcada `'perdido'`, o operador precisa informar um motivo. `PUT /conversas/:contatoId/:numeroRemetenteId/status` aceita `motivo`/`motivoDetalhe` no corpo, além de `status` já existente — `motivo` é OBRIGATÓRIO quando `status === 'perdido'` (`conversas.service.js: atualizarStatus` retorna o sentinel string `'motivo_obrigatorio'` quando ausente, sem chamar o model — mesmo padrão de sentinel-return já usado por `numerosRemetentesService.criarNumero` → `'estado_inexistente'` —, e `conversas.controller.js` mapeia esse sentinel pra `400`); pra qualquer outro `status`, os dois campos são ignorados/gravados `null`. `motivo`, quando presente, é validado contra um enum fixo de 6 valores (`MOTIVOS_PERDIDO_VALIDOS` em `conversas.controller.js`, ao lado de `STATUS_VALIDOS`): `nao_foi_loja`/`foi_loja_nao_comprou`/`preco_condicao`/`comprou_outro_lugar`/`desistiu_sem_resposta`/`outro`. Os dois campos só são persistidos em `StatusHistorico` (via `registrarHistoricoStatus`, chamada de dentro de `upsertStatusConversa` com `origem='atendente'`) — nunca em `ConversasStatus`, que continua sem coluna de motivo (é "estado atual", motivo é detalhe de auditoria/histórico). No frontend, `ModalMotivoPerdido` (`frontend/src/modulos/controle-ligacoes/components/ModalMotivoPerdido.jsx`, `export default` + `export const MOTIVOS_PERDIDO` — o array `{value,label}` dos 6 motivos, única fonte de verdade dos rótulos, reaproveitada por `ConversasPage.jsx`/`PipelinePage.jsx`/`InicioPage.jsx`, nunca duplicada) abre ANTES de chamar a API quando o `<select>` de status (em `ConversasPage.jsx` ou em cada card de `PipelinePage.jsx`) muda pra `'perdido'` — cancelar o modal não reverte nada porque a chamada nunca chegou a sair (o `<select>` é controlado por estado que só muda depois de sucesso, então ele volta a mostrar o valor antigo sozinho); confirmar dispara a `PUT` de verdade com `motivo`/`motivoDetalhe` do modal. `PipelineCard`, quando `item.status === 'perdido'`, mostra "Motivo: {label}" (mais `— {motivoDetalhe}` se preenchido) logo abaixo do `<select>`.

`DateRangeFilter` (`frontend/src/modulos/controle-ligacoes/components/DateRangeFilter.jsx`, `export default`, primeiro componente compartilhado só deste módulo — o único outro caso de componente compartilhado no projeto inteiro é `UserFooterMenu.jsx`, cross-módulo, ver árvore de pastas do Frontend abaixo) é usado tanto em `PipelinePage.jsx` quanto em `InicioPage.jsx` (Dashboard, ver abaixo): botão mostra o período formatado (`"01 de ago. - 21 de ago."`, ou "Selecionar período" vazio) e abre um popover com atalhos à esquerda (Hoje/Ontem/Hoje e ontem/Últimos 7·14·28·30 dias/Esta semana/Semana passada/Este mês/Mês passado/Máximo) e um calendário navegável de 42 células à direita (`Date` nativo, sem lib nova), seleção de intervalo por dois cliques, "Cancelar"/"Aplicar período" no rodapé. Os 6 KPIs do topo (Total de Disparos + 5 taxas) mostram também a contagem bruta entre parênteses ao lado do percentual (ex.: "11.7% (14)") — `kpi.contagemAbsoluta`, o mesmo numerador já usado no cálculo de `kpi.valor` — e usam `baseEngajados = atendeuCount+agendouCount+vendaCount+perdidoCount` como denominador comum (não `totalDisparos` nem `atendeuCount` isolado) — porque `ConversasStatus.status` é um valor final único por thread, não cumulativo: um contato com status `venda` não conta em `atendeuCount` nem `agendouCount`. Pra não produzir um funil que alarga no meio, o `FunnelChart` e os KPIs de "Taxa de Agendamento"/"Conversão dos Agendados/Engajados"/"Taxa de Perda" tratam os estágios como cumulativos (ex.: `agendouCount+vendaCount` representa "chegou a agendar", incluindo quem já vendeu). `STATUS_HEX` (cores fixas por status, hex literais idênticos aos de `ConversasPage.jsx`) mantém a mesma identidade visual por status nas duas telas, apesar de temas claro/escuro diferentes. `InfoTooltip` (ícone de interrogação desenhado à mão + atributo `title` nativo do HTML) documenta a fórmula de cada card/gráfico — mesmo padrão de SVG inline sem `lucide-react` usado em `StatusEntregaIcone`. **Nenhum teste automatizado cobre `dashboard.model.js`/`.service.js`/`.controller.js` nem `InicioPage.jsx`/`dashboardApi.js`** — lacuna conhecida, não convenção.

**7 métricas novas do Dashboard** (adendo posterior, todas baseadas em `StatusHistorico`, mesmo filtro `estadoId`/`dataInicio`/`dataFim` das outras 8, incluídas no mesmo `Promise.all` de `getDashboard`): `tempoMedioPorEtapa` (array `{status, horasMedias}`, `AVG` de `DATEDIFF` via `LEAD() OVER (PARTITION BY contato_id, numero_remetente_id ORDER BY alterado_em)` — o filtro de período é aplicado numa query EXTERNA, depois do `LEAD()` já calculado sobre o histórico completo, nunca dentro da CTE que roda a função de janela, senão corromperia a adjacência "próxima mudança" pra qualquer thread com mudanças dentro E fora do período filtrado); `tempoMedioConversao` (`{horasMedias: number|null}`, `null` explícito quando não há nenhuma conversão atendeu→venda — não confundir com `0`); `velocidadeRespostaAtendente` (array `{apelido, horasMedias}`, tempo entre `Disparos.criado_em` e a primeira ação do atendente — usa `CROSS APPLY` pra pegar só o `Disparo` mais recente anterior à ação, não um `JOIN` direto, porque um contato pode ter sido disparado mais de uma vez pelo mesmo número sem nunca responder, o que duplicaria/inflaria a média); `taxaRecuo` (`{taxaPct: number|null}`, `null` quando ninguém no filtro já chegou a `'agendou'`); `caminhosComuns` (top 5 `{caminho, total}`, `STRING_AGG(status_novo, ' → ') WITHIN GROUP (ORDER BY alterado_em)` por thread — igual à ressalva de `tempoMedioPorEtapa`, o caminho é sempre montado a partir do histórico COMPLETO, o filtro de período (quando informado) só decide quais threads entram, comparando contra a data da ÚLTIMA mudança de cada uma, nunca truncando o caminho em si); `statusPulados` (`{total}`, vendas que nunca passaram por `'agendou'`); `origemPorDia` (30 entradas zero-preenchidas, mesmo padrão de `tendenciaDiaria`, `{dia, sistema, atendente}` — pivotado em JS a partir de `{dia, origem, total}`). No frontend, 3 seções novas em `InicioPage.jsx`, cada uma dentro de um card único, posicionadas depois de "Ranking de Atendentes": "Tempo por Etapa" (`BarChart` + card "Tempo médio até a venda" + tabela por atendente), "Padrões de Comportamento" (2 cards + tabela "Caminhos Mais Comuns") e "Atividade por Origem" (`LineChart` de 2 séries com `Legend`, único gráfico do arquivo que usa `Legend` — os demais têm 1 série só).

**Motivos de Perda** — card `BarChart` novo em `InicioPage.jsx`, logo depois de "Motivos de Saída" (complementa, não substitui — "Motivos de Saída" compara `nao_atendeu` vs. `perdido` no geral, "Motivos de Perda" detalha POR QUE cada `perdido` aconteceu, nos 6 valores do enum `MOTIVOS_PERDIDO` — ver "Motivo de perda" mais acima), a partir do bloco `motivosPerdido` (`[{motivo, total}]`, `GROUP BY sh.motivo WHERE status_novo='perdido'`, sem zero-fill — só motivos com pelo menos 1 registro aparecem) — mesmos rótulos de `MOTIVOS_PERDIDO` (`ModalMotivoPerdido.jsx`), eixo X com `angle={-15}` pra caber o texto mais longo dos rótulos.

**"Aguardando Ação"** (`GET /api/controle-ligacoes/aguardando-acao`, rota separada, **NÃO** parte de `getDashboard`/`GET /dashboard` — sem filtro de Estado/Período, sempre visão atual) — `dashboard.model.js: getAguardandoAcao({horasSemResposta=24, diasAgendadoParado=3})`, `UNION ALL` de 2 grupos: (1) `'sem_resposta'` — contato disparado há mais de `horasSemResposta` sem NENHUM `ConversasStatus` pra aquela combinação `(contato, número)`; agrupado por `(contato_id, numero_remetente_id)` com `MAX(Disparos.criado_em)` como referência — necessário porque um contato pode ter sido redisparado mais de uma vez pelo mesmo número sem nunca responder, e sem o `GROUP BY` a mesma thread pendente apareceria duplicada, uma linha por `Disparo` histórico; o corte usa `HAVING MAX(...) <= cutoff`, não `WHERE`, pra julgar pela tentativa MAIS RECENTE, não a mais antiga; (2) `'agendado_parado'` — thread com `ConversasStatus.status='agendou'` há mais de `diasAgendadoParado` dias (sem risco de duplicar, `ConversasStatus` já é 1 linha por thread). Resposta: array `{contatoId, numeroRemetenteId, nome, telefone, apelido, referencia, tipo}` (camelCase, seguindo a convenção do próprio `dashboard.model.js`, diferente do pass-through snake_case de `mensagens.model.js`), `ORDER BY referencia ASC` (mais antigo/crítico primeiro). No frontend, tabela "Aguardando Ação" no TOPO de `InicioPage.jsx` (acima dos 6 KPIs, busca própria só no mount, independente dos filtros Estado/Período/`dashboard` state) — linha clicável navega pra `/controle-ligacoes/conversas` com o mesmo shape de `state` que `selecionarNotificacao` (sino de notificações) já usa; "Situação" formatada via o mesmo helper de tempo relativo do sino (`formatRelativoNotificacao`, replicado localmente em `InicioPage.jsx`, não exportado de `ControleLigacoesShell.jsx`). Container com `max-h-72 overflow-y-auto` + `<thead>` `sticky top-0`; cada `<tr>` tem uma cor de fundo em gradiente (`rgba(224, 100, 90, intensidade * 0.15)`, mesmo hex de `--danger`) proporcional à posição na lista — mais vermelho no topo (mais urgente/antigo), neutro no fim — já que a lista já vem ordenada por `referencia ASC`.

Variáveis de ambiente obrigatórias (ver `backend/.env.example`): `PORT`, `DB_SERVER`, `DB_DATABASE`, `DB_USER`, `DB_PASSWORD`, `DB_PORT`, `DB_ENCRYPT`, `DB_TRUST_SERVER_CERTIFICATE`, `JWT_SECRET` (segredo de assinatura dos tokens JWT, nunca versionado), `BREVO_API_KEY`, `EMAIL_REMETENTE`, `EMAIL_REMETENTE_NOME`, `EMAIL_DESTINATARIOS` (envio de relatório por e-mail, ver abaixo), `NODE_ENV` e `FRONTEND_URL` (controlam a allowlist de CORS, ver abaixo). Opcionais, com default no código se ausentes (worker de "Envio de Disparos", ver acima): `ENVIO_DISPAROS_INTERVALO_MS`, `ENVIO_DISPAROS_LOTE_TAMANHO`, `ENVIO_DISPAROS_DELAY_ENTRE_MENSAGENS_MS`. `getPool()` em `config/db.js` lança erro imediatamente se alguma variável `DB_*` estiver ausente, e reseta a promise da pool em cache em caso de falha de conexão, para que a próxima chamada possa tentar novamente.

**Segurança de borda é aplicada globalmente em `app.js`, antes de qualquer rota.** `helmet()` roda com configuração padrão. O CORS é restrito por allowlist: se `NODE_ENV=production`, só `FRONTEND_URL` é aceito; fora de produção, `http://localhost:5173` (porta padrão do Vite) é sempre aceito além de `FRONTEND_URL`. `POST /api/auth/login` tem rate limit dedicado via `express-rate-limit` (10 tentativas por IP a cada 15 minutos, `429` com corpo `{ "error": "..." }` ao estourar) — aplicado como `app.use('/api/auth/login', loginLimiter)` **antes** do mount de `authRoutes` em `app.js`, não dentro de `auth.routes.js`. `POST /api/auth/esqueci-senha` segue o mesmo padrão com uma instância própria (`esqueciSenhaLimiter`, 5 tentativas por IP a cada 15 minutos — menor que o login porque cada tentativa pode disparar um e-mail real). Nenhuma outra rota tem rate limit hoje. `app.js` também nunca sobrescreve o `etag` (default global do Express, `'weak'`) — toda rota do backend pode responder `304 Not Modified` de corpo vazio pra um cliente que reenvie `If-None-Match`, o que é inadequado pra dado dinâmico/autenticado. Só `/api/controle-ligacoes/*` tem correção pra isso hoje (middleware próprio no router, ver "Módulo Controle de Ligações" abaixo) — `/api/ranking`, `/api/margens`, `/api/marketing`, `/api/cadastros`, `/api/auth` e `/api/admin` continuam expostas ao mesmo comportamento; se for mexer numa rota desses módulos e o cliente relatar dado desatualizado/vazio sem erro aparente, esse é um suspeito conhecido, não presuma que é bug novo.

`POST /api/ranking/relatorio/email` (protegida por `authMiddleware`, igual ao resto de `/api/ranking`) envia o texto do relatório do dia por e-mail via API transacional do Brevo (`https://api.brevo.com/v3/smtp/email`). `backend/src/services/brevoEmail.service.js` é uma camada de acesso a serviço externo com o mesmo papel que um model tem para o banco (não conhece `req`/`res`, só monta a chamada HTTP e propaga o erro do Brevo) — `ranking.service.js`/`ranking.controller.js` chamam essa função como fariam com qualquer outro service. Erros retornados pelo Brevo viram `502`; validação de `texto` ausente vira `400`. No frontend, `rankingApi.js` expõe `enviarRelatorioPorEmail`, chamada a partir de `RankingPage.jsx` junto do fluxo de "Gerar relatório do dia". Contrato completo (payload, status codes) na seção 11 de `CONTRATO-RANKING-API.md`.

### Frontend: o registro de módulos comanda rotas + navegação

```
frontend/src/
├── app/
│   ├── AppShell.jsx        # layout: Sidebar + <Outlet/>
│   ├── Sidebar.jsx          # renderiza os links de navegação a partir do moduleRegistry
│   ├── UserFooterMenu.jsx   # bloco de usuário no rodapé da sidebar (e-mail antes do "@" + status estático "Disponível" + dropdown com "Sair") — compartilhado por Sidebar.jsx E ControleLigacoesShell.jsx, não duplicado
│   ├── moduleRegistry.js    # fonte única de verdade dos módulos do ERP normal (NÃO inclui Controle de Ligações, ver abaixo)
│   └── ControleLigacoesShell.jsx  # segunda casca de layout, paralela à AppShell — nav própria, fora do moduleRegistry
├── routes/
│   ├── AppRoutes.jsx        # monta as entradas <Route> a partir do moduleRegistry, MAIS uma árvore própria (fora de RequireAuth) pro Controle de Ligações
│   └── RequireOperadorCobranca.jsx  # guard do Controle de Ligações, espelha RequireAdmin.jsx mas checa isOperadorCobranca
├── lib/
│   ├── apiClient.js         # fetch com Authorization + tratamento de 401 global
│   └── cadastrosApi.js      # CRUD de Diretor/Rede/Loja/Responsavel — compartilhado, não pertence a um módulo
└── modulos/<modulo>/         # hoje: ranking, margens, marketing, admin (usuarios), auth, controle-ligacoes
    ├── <Modulo>Page.jsx
    └── <modulo>Api.js        # helper de fetch isolado da UI, só do que é exclusivo do módulo (ver rankingApi.js/margensApi.js)
```

Para adicionar uma nova tela de módulo do ERP normal: crie `modulos/<modulo>/<Modulo>Page.jsx` e adicione uma entrada em `moduleRegistry.js` (`{ id, label, path, icon, element }`) — hoje tem cinco entradas: `ranking`, `ranking-configuracoes`, `margens`, `marketing`, `usuarios` (`usuarios` e `ranking-configuracoes` são `adminOnly`). `ranking-configuracoes` (rota `/ranking/configuracoes`, rotulada "Diretores e redes") não é um módulo de negócio à parte — reaproveita o mesmo componente `element: RankingPage`, que decide internamente qual sub-tela mostrar a partir do `pathname` atual; existe como entrada própria no registry só para ganhar `adminOnly: true` (link some do menu e a rota é protegida por `<RequireAdmin/>`) sem precisar de um módulo novo. `Sidebar` e `AppRoutes` leem esse array — nada mais precisa mudar para ganhar um link de navegação + rota. `icon` é uma **string simples** (emoji, ex.: `'📊'`), renderizada como texto puro em `Sidebar.jsx` (`<span>{mod.icon}</span>`) — não é um componente de ícone (não há `lucide-react` nem equivalente instalado no projeto); `element` é a referência ao componente (`MargensPage`, não `<MargensPage/>`), instanciado por `AppRoutes.jsx`. Um módulo pode opcionalmente ter `adminOnly: true` (ver o módulo `usuarios`) — isso faz `Sidebar.jsx` nunca renderizar o link para usuário não-admin (não é só CSS escondido) e `AppRoutes.jsx` envolver a rota com `<RequireAdmin/>`, bloqueando acesso direto pela URL. **O Controle de Ligações é a única exceção a esse padrão**: não tem entrada em `moduleRegistry.js` (por isso `Sidebar.jsx` nunca o lista, mesmo pra admin) — em vez disso, `AppRoutes.jsx` monta uma segunda árvore de rotas totalmente separada, `<Route element={<RequireOperadorCobranca/>}><Route path="controle-ligacoes" element={<ControleLigacoesShell/>}>...</Route></Route>`, fora da árvore `RequireAuth`/`AppShell` do resto do ERP. Ao criar um módulo novo, o padrão default continua sendo `moduleRegistry.js`; só replique o padrão do Controle de Ligações se o requisito for isolamento total (login/role própria, invisível pro resto dos usuários). Isso não impede reaproveitar um componente de página já existente do ERP normal dentro dessa árvore separada quando fizer sentido — ver a rota `/controle-ligacoes/usuarios` (reaproveita `UsuariosPage.jsx`, protegida por `RequireAdmin` aninhado) na Visão Geral acima.

Chamadas de API ficam isoladas num arquivo `<modulo>Api.js` ao lado da página (ex.: `rankingApi.js`, `margensApi.js`, `marketingApi.js`), usando `fetch` nativo (sem axios) e `import.meta.env.VITE_API_URL` como base — não chame `fetch` direto de dentro do componente. A exceção é cadastro compartilhado (Diretor/Rede/Loja/Responsavel): fica em `frontend/src/lib/cadastrosApi.js`, ao lado de `apiClient.js`, por não pertencer a um módulo de negócio específico (ver módulo Cadastros na Visão Geral). `apiClient.js` não força mais `Content-Type: application/json` quando o `body` é uma instância de `FormData` (deixa o navegador definir o `multipart/form-data` com boundary sozinho) — mudança genérica, feita pro upload de planilha do Controle de Ligações (`POST /contatos/importar`), mas vale pra qualquer chamada futura que precise enviar arquivo. Variável de ambiente obrigatória (ver `frontend/.env.example`): `VITE_API_URL`.

### Estilo: Tailwind é o padrão do projeto; MUI só quando compensa

Tailwind CSS v4 (config em `index.css` via `@theme`/variáveis CSS em `:root`, ex.: `--bg`, `--panel`, `--teal` — sem `tailwind.config.js`) é o sistema de estilo padrão para todas as telas, inclusive telas que replicam um visual de protótipo já existente (reproduza com classes Tailwind/valores arbitrários, sem criar um arquivo `.css` separado). O MUI (`@mui/material`) fica reservado para casos em que um componente pronto e complexo compensa o custo (`DataGrid`, `DatePicker`, `Autocomplete`, `Dialog` complexo).

**Regra rígida, aplicada em todo o projeto (`.claude/skiils/frontend-conventions/SKILL.md`):** nunca misture MUI e Tailwind no mesmo componente/elemento — nada de classes Tailwind em componentes MUI, nem `sx` + `className` no mesmo elemento. Cada arquivo tem um único dono de estilo; declare isso com um comentário no topo: `// style-system: MUI` ou `// style-system: Tailwind` (ver início de `RankingPage.jsx`).

## Subagentes e skills

Este repositório define subagentes específicos do projeto em `.claude/agents/` e skills em `.claude/skiils/` (note que a pasta se chama `skiils`, não `skills`):
- `agent-organizer` — orquestra tarefas que tocam mais de uma camada (ex.: endpoint novo + a tela que o consome), dividindo o trabalho entre os demais subagentes.
- `backend-architect` — especialista em Node/Express/Azure SQL; cuida de routes/controllers/services/models.
- `frontend-developer` — especialista em React; cuida de componentes/telas, aplicando a divisão MUI/Tailwind acima.
- `qa-tester` (arquivo `.claude/agents/test-engineer.md` — nome do arquivo ficou desatualizado; o agente é invocado pelo `name:` do frontmatter, que é `qa-tester`) — especialista em QA; escreve testes automatizados, roda validações manuais possíveis e dá veredito de "pronto para produção" ou não. Deve ser acionado como última fase depois que `backend-architect`/`frontend-developer` terminam uma feature nova. Vitest/Supertest (backend) e Vitest/React Testing Library (frontend) já estão instalados e configurados (ver seção Comandos, `npm test` em cada app) — este agente deve estender essa suíte existente para features novas, não presumir que precisa introduzir a infraestrutura do zero. (O texto interno do próprio `test-engineer.md` ainda afirma que essa infraestrutura de testes não existe — está desatualizado/contradiz este parágrafo; corrija se for editar esse arquivo.)

As skills `backend-conventions`, `frontend-conventions` e `testing-conventions` valem mesmo fora desses subagentes — ou seja, em qualquer edição direta de arquivo de backend, `.jsx`, ou ao escrever testes.

REGRA DE SEGURANÇA: nenhum subagente deve editar backend/.env, rodar
migrations, ou executar qualquer comando que se conecte a um banco fora
de localhost, sem pedir confirmação explícita ao usuário antes. Toda
alteração de schema/dados deve ser feita e validada primeiro no banco
local (erp-novagest-dev).
